## Cómo usar este archivo

- Los patrones `rg` generan **candidatos**, no hallazgos. Cada coincidencia pasa por las cuatro preguntas de triage de SKILL.md (entrada controlada, camino alcanzable, alcance, precondiciones) antes de ir a `candidates.json`.
- Pasa siempre una ruta a `rg` (`.` o la carpeta del componente). Sin ruta, y con stdin que no es una terminal (shell de agente), `rg` lee stdin y se queda esperando.
- Excluye ruido: añade `-g '!**/node_modules/**' -g '!**/vendor/**' -g '!**/dist/**'` y revisa aparte los tests (`-g '!**/test*/**'`).
- Si afirmas que un control **falta**, guarda la búsqueda exacta como evidencia `kind: absence` con `query` y `hits: 0`. Una búsqueda demasiado estrecha no prueba ausencia: prueba al menos dos formulaciones.
- Escribe los IDs ASVS como `v5.0.0-8.2.2` en `findings.json`. Las CWEs citadas aquí son un subconjunto de `data/cwe-to-top10-2025.json`; si usas otra CWE, comprueba en ese archivo a qué categoría mapea (el validador avisa si no coincide).
- A03 y A09 salen de la **encuesta comunitaria**, no de datos de testing, y tienen solo 5–6 CWEs. Evalúalos con artefactos de pipeline y de proceso (lockfiles, workflows, configuración de logs y alertas), no con patrones de código.
- Nunca escribas que el proyecto "cumple el Top 10". El Top 10 resume; ASVS mide.

## A01:2025 Broken Access Control

**Qué es**: un usuario actúa fuera de sus permisos: lee o modifica datos ajenos, sube de privilegio o hace que el servidor llame a destinos que no debería (SSRF).
**2021**: A01 Broken Access Control + A10 SSRF (CWE-918 está ahora en A01).

**Preguntas de diseño**
- ¿Dónde se decide la autorización? ¿Un único punto de política en el servidor, o un `if` por handler?
- ¿Es deny-by-default? ¿Una ruta nueva queda protegida sin que nadie haga nada?
- ¿Cada acceso por ID comprueba propiedad o pertenencia al tenant? ¿El tenant sale del contexto autenticado o del body?
- ¿Qué destinos salientes puede alcanzar el backend con una URL que aporta el usuario? ¿Hay egress allowlist y bloqueo de metadata (169.254.169.254)?
- ¿CORS, CSRF y SameSite son coherentes con el modelo de sesión (cookie vs bearer)?

**Señales**
```bash
rg -n -t js -t ts 'find(ById|ByPk|One|Unique)\(\s*\{?\s*(where:\s*\{\s*id:\s*)?req\.(params|query|body)'   # carga por ID: ¿predicado de propietario/tenant?
rg -n -t py 'objects\.get\(\s*(pk|id)=|get_object_or_404\(|session\.get\(\s*\w+,\s*\w*id\)'
rg -n -t java 'findById\(\s*\w*[iI]d\s*\)|@PathVariable'
rg -n -t go 'chi\.URLParam\(|mux\.Vars\(|c\.Param\(|r\.PathValue\('
rg -n -t java '@(PreAuthorize|Secured|RolesAllowed)|permitAll\(\)|anyRequest\(\)\.permitAll'
rg -n -t py 'permission_classes|@login_required|Depends\(\s*(get_current_user|require_)'
rg -n -t js -t ts '(router|app)\.(get|post|put|patch|delete)\('   # compara nº de rutas con nº de controles
rg -n -i 'Access-Control-Allow-Origin|allow_origins|AllowedOrigins|origin:\s*(true|\*)|allowCredentials'   # CORS
rg -n -t js -t ts '(fetch|axios(\.(get|post|request))?|got|needle)\(\s*[a-zA-Z_]'   # SSRF: ¿URL del usuario?
rg -n -t py '(requests|httpx)\.(get|post|request)\(|urlopen\('
rg -n -t java 'new URL\(|RestTemplate|WebClient|HttpClient\.newHttpClient'
rg -n -t go 'http\.(Get|Post|NewRequest(WithContext)?)\('
rg -n 'res\.redirect\(\s*req\.|HttpResponseRedirect\(\s*request\.|sendRedirect\(|http\.Redirect\('
rg -n 'path\.join\(.*req\.|os\.path\.join\(.*request|new File\(.*getParameter|filepath\.Join\(.*r\.(URL|Form)'
rg -n -i 'csrf\(\)\.disable|csrf_exempt|csrf:\s*false'
```

- **Compensatorios**: middleware global (`app.use(auth)`, `SecurityFilterChain` con `anyRequest().authenticated()`), autorización en gateway (OPA, Envoy, Kong), RLS en base de datos (`ENABLE ROW LEVEL SECURITY`, `CREATE POLICY`), repositorios con scope por tenant, proxy de egress o NetworkPolicy que bloquea redes internas. Un UUID impredecible **no** es control de acceso.
- **Capa de test**: integración (BOLA con dos usuarios, matriz rol × endpoint y test de cobertura de rutas, SSRF contra 127.0.0.1 y 169.254.169.254) en `plantillas-de-tests.md`; SAST para SSRF y path traversal; DAST solo con contextos autenticados de al menos dos usuarios. Detalle de autorización por objeto, propiedad y función en `api-top10-2023.md`.
- **ASVS 5.0.0**: v5.0.0-8.2.1, v5.0.0-8.2.2, v5.0.0-8.3.1, v5.0.0-8.4.1, v5.0.0-1.3.6, v5.0.0-3.4.2 · **CWEs**: CWE-22, CWE-200, CWE-284, CWE-285, CWE-352, CWE-601, CWE-639, CWE-862, CWE-863, CWE-918, CWE-1275

## A02:2025 Security Misconfiguration

**Qué es**: configuración insegura o por defecto en cualquier capa: framework, servidor, contenedor, nube, parsers, headers y cookies.
**2021**: A05 Security Misconfiguration (sube del #5 al #2). XXE (CWE-611, CWE-776) sigue aquí.

**Preguntas de diseño**
- ¿El hardening es automático y repetible (IaC, imágenes base) o manual?
- ¿Qué distingue la configuración de producción de la de desarrollo, y quién puede cambiarla?
- ¿Hay credenciales distintas por entorno? ¿Se usan identidades federadas o credenciales de corta vida en vez de secretos estáticos?
- ¿Dónde se ponen los security headers: en la app, en el proxy o en la CDN?

**Señales**
```bash
rg -n -i 'DEBUG\s*=\s*True|debug=True|gin\.SetMode\(gin\.DebugMode\)|spring\.profiles\.active=dev'
rg -n 'management\.endpoints\.web\.exposure\.include=\*|net/http/pprof|/debug/'
rg -n -t java 'DocumentBuilderFactory|SAXParserFactory|XMLInputFactory|TransformerFactory'   # busca disallow-doctype-decl
rg -n -t py 'lxml\.etree|xml\.etree|xml\.dom\.minidom|resolve_entities'                        # defusedxml es el control
rg -n -t js -t ts 'libxmljs|noent:\s*true'
rg -n -i 'httpOnly:\s*false|secure:\s*false|SESSION_COOKIE_SECURE\s*=\s*False|setHttpOnly\(false\)|HttpOnly:\s*false'
rg -n -i 'helmet\(|Content-Security-Policy|Strict-Transport-Security|SECURE_HSTS_SECONDS|X-Content-Type-Options'   # 0 hits = candidato a ausencia
rg -n -i '(POSTGRES_PASSWORD|MYSQL_ROOT_PASSWORD|ADMIN_PASSWORD)\s*[:=]\s*\S*(admin|root|password|changeme|postgres)'
rg -n -i 'public-read|block_public_acls\s*=\s*false|0\.0\.0\.0/0|privileged:\s*true|runAsUser:\s*0|allowPrivilegeEscalation:\s*true'
```

- **Compensatorios**: headers añadidos por nginx/Envoy/CDN (lee su configuración), override de producción (`settings/prod.py`, `application-prod.yml`, variables del despliegue), archivo de config que no se despliega. Verifica qué archivo llega de verdad a producción antes de reportar.
- **Capa de test**: escaneo de IaC y contenedores (Checkov, Trivy config, hadolint, kube-linter), DAST pasivo (ZAP baseline) y un test de integración que afirme headers y flags de cookie. Comandos en `herramientas-y-gates.md`.
- **ASVS 5.0.0**: v5.0.0-13.4.2, v5.0.0-15.2.3, v5.0.0-3.4.1, v5.0.0-3.4.3, v5.0.0-3.3.1, v5.0.0-1.5.1 · **CWEs**: CWE-16, CWE-260, CWE-489, CWE-526, CWE-611, CWE-614, CWE-942, CWE-1004

## A03:2025 Software Supply Chain Failures

**Qué es**: compromiso o debilidad en dependencias, builds, distribución, CI/CD o herramientas de desarrollo. Incluye paquetes maliciosos y un pipeline más débil que el sistema que despliega.
**2021**: A06 Vulnerable and Outdated Components, ampliada. **Categoría de encuesta**: evalúala con artefactos, no con código.

**Preguntas de diseño**
- ¿Hay lockfile versionado y se instala con él (`npm ci`, `pip install --require-hashes`)? ¿Se siguen las transitivas?
- ¿Existe SBOM? ¿Alguien recibe alertas de CVEs nuevas después del despliegue?
- ¿Una sola persona puede llevar código a producción (separación de funciones, revisiones obligatorias)?
- ¿Las Actions están fijadas por SHA? ¿Los secretos de CI están limitados por entorno? ¿`GITHUB_TOKEN` tiene `permissions` mínimos?
- ¿Las dependencias internas pueden confundirse con paquetes públicos (dependency confusion)?

**Señales**
```bash
rg --files | rg '(package-lock\.json|pnpm-lock\.yaml|yarn\.lock|poetry\.lock|uv\.lock|Pipfile\.lock|go\.sum|gradle\.lockfile|Cargo\.lock)$'
rg -n 'uses:\s*[^@\s]+@(v?[0-9][^ ]*|main|master)\s*$' .github/workflows     # no fijadas por SHA
rg -n 'pull_request_target' .github/workflows                                  # y luego: ¿checkout de github.event.pull_request.head?
rg -n '^permissions:|^\s+permissions:' .github/workflows                       # 0 hits = permisos por defecto del token
rg -n 'npm install\b|pip install (?:-r )?\S+$' .github/workflows
rg -n 'curl [^|]*\|\s*(ba)?sh'
rg -n '"(pre|post)?install"\s*:' -g 'package.json'
rg -n -e '--extra-index-url|--index-url' -g '*requirements*.txt' -g 'pip.conf' -g 'Dockerfile'
rg -n '^FROM\s+\S+(:latest)?\s*$' -g 'Dockerfile*'                              # sin tag ni digest
rg --files | rg '(dependabot\.ya?ml|renovate\.json5?|\.renovaterc)$'
```

- **Compensatorios**: branch protection y reglas de organización (no se ven en el repo: márcalo `not_verifiable` y pregunta), registro proxy interno, workflows obligatorios a nivel de organización.
- **Capa de test**: SCA (OSV-Scanner, Trivy, Grype, npm audit, pip-audit, govulncheck), SBOM (Syft, cdxgen), OpenSSF Scorecard y verificación de procedencia. Ningún test unitario lo cubre. Ver `herramientas-y-gates.md`. Hallazgos con prefijo `SUP-`.
- **ASVS 5.0.0**: v5.0.0-15.1.1, v5.0.0-15.1.2, v5.0.0-15.2.1, v5.0.0-15.2.4, v5.0.0-15.1.4 · **CWEs**: CWE-1104, CWE-1329, CWE-1357, CWE-1395, CWE-1035

## A04:2025 Cryptographic Failures

**Qué es**: datos sensibles sin protección criptográfica adecuada: algoritmos rotos, claves mal gestionadas, aleatoriedad débil, TLS ausente o sin validar.
**2021**: A02 Cryptographic Failures.

**Preguntas de diseño**
- ¿Qué datos están clasificados como sensibles y dónde viajan y se guardan?
- ¿Dónde viven las claves (KMS, vault, HSM) y cómo rotan? ¿Hay inventario criptográfico?
- ¿Qué KDF protege las contraseñas y con qué parámetros?
- ¿Hay TLS validado también entre servicios internos?

**Señales**
```bash
rg -n -i 'createHash\(\s*.(md5|sha1).|hashlib\.(md5|sha1)\(|MessageDigest\.getInstance\(\s*"(MD5|SHA-?1)"|crypto/(md5|sha1)"'
rg -n -i 'AES/ECB|DESede|"DES"|RC4|aes-\d+-(ecb|cbc)|MODE_ECB|cipher\.NewCBC(En|De)crypter'
rg -n 'Math\.random\(|random\.(random|randint|choice)\(|new Random\(|"math/rand"'   # crítico si genera tokens, OTP o IDs de reset
rg -n 'rejectUnauthorized:\s*false|NODE_TLS_REJECT_UNAUTHORIZED|verify\s*=\s*False|InsecureSkipVerify:\s*true|TrustAllCerts|NoopHostnameVerifier'
rg -n -i '(secret|private|api|signing)_?key\s*[:=]\s*["\x27][^"\x27]{12,}|BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY'
rg -n -i 'argon2|bcrypt|scrypt|pbkdf2'                 # 0 hits con contraseñas almacenadas = candidato
rg -n -i '\biv\s*=\s*(b?["\x27]|new byte\[|bytes\(16\))'
```

- **Compensatorios**: mTLS gestionado por la malla de servicios (rebaja, no refuta, un `verify=False` interno); MD5/SHA1 usado para algo que no es seguridad (ETag, clave de caché): confirma el propósito antes de reportar.
- **Regla de verificación**: CWE-327, 328, 326, 916, 330, 338, 319 y otras están en `protected_cwes` de `data/verification-policy.json`. No pasan a REFUTED sin una persona.
- **Capa de test**: SAST fuerte (Semgrep, Bandit, gosec, CodeQL), secret scanning (gitleaks, trufflehog), unit test que fija el algoritmo y coste del hash de contraseñas, DAST para la configuración TLS.
- **ASVS 5.0.0**: v5.0.0-11.3.1, v5.0.0-11.3.2, v5.0.0-11.4.2, v5.0.0-11.5.1, v5.0.0-12.3.2, v5.0.0-13.3.1 · **CWEs**: CWE-319, CWE-321, CWE-326, CWE-327, CWE-328, CWE-330, CWE-338, CWE-916

## A05:2025 Injection

**Qué es**: datos no confiables llegan a un intérprete (SQL, NoSQL, shell, plantilla, HTML/JS, LDAP, expresiones) sin separarse del comando. Incluye XSS.
**2021**: A03 Injection.

**Preguntas de diseño**
- ¿Hay una capa de acceso a datos que siempre parametriza, o SQL a mano repartido?
- ¿El escapado de salida lo hace el framework (autoescape) o cada vista?
- ¿Hay nombres de tabla, columna u `ORDER BY` que vienen del usuario? No se pueden parametrizar: exigen allowlist.

**Señales**
```bash
rg -n -t js -t ts '\.(query|execute|raw|\$queryRawUnsafe|\$executeRawUnsafe)\(\s*["\x27].*(\$\{|["\x27]\s*\+)'
rg -n -t py 'execute\(\s*f["\x27]|execute\([^,)]*(%|\+|\.format\()|\.raw\(|text\(\s*f["\x27]'
rg -n -t java '(createQuery|createNativeQuery|executeQuery|executeUpdate|prepareStatement)\(\s*"[^"]*"\s*\+'
rg -n -t go '(Query|Exec|QueryRow)(Context)?\([^)]*(fmt\.Sprintf|"\s*\+)'
rg -n 'child_process|execSync\(|shell:\s*true|shell=True|os\.system\(|os\.popen\(|Runtime\.getRuntime\(\)\.exec|exec\.Command\(\s*"(sh|bash|cmd)"'
rg -n 'eval\(|new Function\(|vm\.runIn|ScriptEngine|SpelExpressionParser|parseExpression\('
rg -n 'dangerouslySetInnerHTML|innerHTML\s*=|v-html|\[innerHTML\]|bypassSecurityTrust|mark_safe\(|\|\s*safe\b|autoescape\s+false|template\.HTML\(|th:utext'
rg -n 'render_template_string\(|Environment\(.*\)\.from_string\(|Template\(\s*request'
rg -n '\$where|\{\s*\$ne\b|\.find\(\s*req\.(body|query)'
rg -n -i 'order\s+by.*(\$\{|\+\s*\w|%s)|order_by\(\s*request'
```

- **Compensatorios**: ORM con parámetros enlazados (verifica que la llamada concreta los usa), allowlist de identificadores, autoescape activo. CSP mitiga XSS pero **no** refuta el hallazgo: baja la probabilidad.
- **Capa de test**: SAST con taint (CodeQL, Semgrep `p/owasp-top-ten`) y DAST activo son fuertes aquí; test de regresión con el payload del hallazgo; tests de propiedades (Hypothesis, fast-check) para encoders propios. La triage con LLM pierde pocos casos de injection, pero un camino no trazado sigue siendo UNVERIFIED.
- **ASVS 5.0.0**: v5.0.0-1.2.1, v5.0.0-1.2.4, v5.0.0-1.2.5, v5.0.0-1.3.2, v5.0.0-1.3.7, v5.0.0-3.2.2 · **CWEs**: CWE-20, CWE-77, CWE-78, CWE-79, CWE-89, CWE-94, CWE-643, CWE-917

## A06:2025 Insecure Design

**Qué es**: el control que hacía falta no se diseñó, o se diseñó mal. No hay patrón de código que lo delate: se ve contra el threat model y los invariantes de negocio.
**2021**: A04 Insecure Design.

**Preguntas de diseño**
- ¿Hay threat model y ADRs para autenticación, autorización, tenancy y pagos?
- ¿Los invariantes de negocio (precio, cantidad, orden de pasos, límites por usuario) se imponen en el servidor?
- ¿Los tenants están separados por diseño o solo por un `WHERE` que alguien puede olvidar?
- ¿Los recursos limitados (stock, plazas, saldo) resisten carreras (TOCTOU, doble gasto)?
- ¿Los flujos de alto valor exigen segunda aprobación? ¿La funcionalidad peligrosa está aislada?

**Señales**
```bash
rg --files | rg -i '(threat|adr|decisions?|security)[-_/].*\.md$|SECURITY\.md$'
rg -n -i '\b(price|amount|total|discount|unit_price)\b.*req\.(body|query)|request\.(json|data|POST)\[.?(price|amount|total)'
rg -n 'multer\(|UploadFile|MultipartFile|FormFile\(|request\.files'           # revisa tipo, tamaño, ubicación y ejecución
rg -n -i 'idempotency'                                                           # 0 hits en pagos = candidato
rg -n -i 'for update|select_for_update|@Lock\(|LockModeType|SKIP LOCKED|optimistic'
```

- **Compensatorios**: límites en gateway, restricciones de base de datos (`CHECK`, `UNIQUE`), motor de workflow que impone el orden de pasos.
- **Cómo reportarlo**: como hallazgo `DES-`. Un defecto de diseño suele ser la causa raíz de varios `IMPL-`: enlázalos en vez de repetirlos.
- **Capa de test**: revisión humana y abuse-case tests derivados del threat model (sin plantilla propia: usa la estructura de integración de `plantillas-de-tests.md` con el invariante concreto, p. ej. "el mismo cupón no se aplica dos veces"). Los escáneres no lo detectan.
- **ASVS 5.0.0**: v5.0.0-2.1.3, v5.0.0-2.3.1, v5.0.0-2.3.2, v5.0.0-2.3.4, v5.0.0-5.2.2, v5.0.0-15.2.5 · **CWEs**: CWE-269, CWE-362, CWE-434, CWE-501, CWE-602, CWE-657, CWE-841

## A07:2025 Authentication Failures

**Qué es**: el sistema no confirma bien quién es el usuario o no gestiona bien su sesión: fuerza bruta, credenciales embebidas, sesiones que no rotan ni expiran, tokens mal validados.
**2021**: A07 Identification and Authentication Failures (renombrada).

**Preguntas de diseño**
- ¿Librería o IdP contrastado, o autenticación propia?
- ¿Hay rate limit o bloqueo progresivo en login, OTP y recuperación de cuenta?
- ¿La sesión rota al autenticar y se invalida en el servidor al cerrar sesión?
- ¿Los JWT se validan con firma, allowlist de algoritmos, `exp`, `aud` e `iss`?
- ¿Hay varios caminos de autenticación (API keys, SSO, magic links) y todos tienen la misma fuerza?

**Señales**
```bash
rg -n -t js -t ts 'jwt\.decode\(|ignoreExpiration:\s*true|algorithms:\s*\[[^\]]*none'
rg -n -t py 'jwt\.decode\([^)]*(verify_signature["\x27]?\s*:\s*False|verify\s*=\s*False)|algorithms=\[[^\]]*none'
rg -n -t java 'parseClaimsJwt\(|parseUnsecuredClaims|\.unsecured\(\)'
rg -n -t go 'ParseUnverified\(|jwt\.Parse\('                                   # revisa que keyfunc compruebe token.Method
rg -n -i '(password|passwd|pwd)\s*[:=]\s*["\x27][^"\x27]{4,}["\x27]' -g '!**/test*/**'
rg -n -i 'rate.?limit|express-rate-limit|slowapi|bucket4j|limiter|throttl'      # 0 hits cerca de /login = candidato
rg -n 'session\.regenerate\(|cycle_key\(|changeSessionId|sessionFixation\(\)'
rg -n -i 'reset.*token.*(uuid4|Math\.random|randint)'
```

- **Compensatorios**: IdP gestionado (Auth0, Cognito, Keycloak, Entra ID) que aplica bloqueo y MFA (lee su configuración si está en el repo); gateway que valida el JWT antes del servicio.
- **Capa de test**: integración (429 tras N fallos, la sesión rota tras login, el logout invalida, JWT con `alg: none`, firma inválida, `aud` ajeno o expirado son rechazados; plantillas de rate limit, sesión y JWT en `plantillas-de-tests.md`); Schemathesis `ignored_auth`; SAST para credenciales embebidas.
- **ASVS 5.0.0**: v5.0.0-6.3.1, v5.0.0-6.3.3, v5.0.0-7.2.4, v5.0.0-7.4.1, v5.0.0-9.1.2, v5.0.0-9.2.3 · **CWEs**: CWE-287, CWE-306, CWE-307, CWE-384, CWE-613, CWE-640, CWE-798

## A08:2025 Software or Data Integrity Failures

**Qué es**: el sistema confía en código o datos cuya integridad no verifica: deserialización insegura, scripts de terceros sin SRI, actualizaciones sin firma, mass assignment. Es integridad a nivel de artefacto y dato; A03 es la cadena completa.
**2021**: A08 Software and Data Integrity Failures.

**Preguntas de diseño**
- ¿Algún dato serializado que viene del cliente se reconstruye como objeto?
- ¿Los artefactos y actualizaciones se firman y se verifican antes de usarlos?
- ¿Los webhooks entrantes verifican la firma?
- ¿El body de la petición se enlaza directamente al modelo de persistencia?

**Señales**
```bash
rg -n -t py 'pickle\.loads?\(|yaml\.load\(|jsonpickle|marshal\.loads|shelve\.open|torch\.load\('   # yaml.load sin SafeLoader
rg -n -t java 'ObjectInputStream|readObject\(|XMLDecoder|enableDefaultTyping|activateDefaultTyping|JsonTypeInfo\.Id\.CLASS'
rg -n -t js -t ts 'node-serialize|unserialize\(|funcster'
rg -n '<script[^>]+src="https?://' -g '*.html' -g '*.tsx' -g '*.jsx' -g '*.vue'       # y luego: ¿integrity=?
rg -n -i 'webhook' ; rg -n 'constructEvent\(|timingSafeEqual|compare_digest|hmac\.Equal|MessageDigest\.isEqual'
rg -n -t js -t ts 'Object\.assign\(\s*\w+,\s*req\.body|\.(update|create|save)\(\s*req\.body|\.\.\.req\.body'
rg -n -t py '\*\*request\.(json|data|POST|form)|\w+\(\*\*(data|payload|body)\)|fields\s*=\s*["\x27]__all__'
rg -n -t java 'BeanUtils\.copyProperties\(|@ModelAttribute'
rg -n -t go 'ShouldBind(JSON)?\(&|\.Bind(JSON)?\(&|json\.NewDecoder\(r\.Body\)\.Decode\(&'   # ¿al modelo de BD?
```

- **Compensatorios**: DTO o esquema con allowlist (zod `.strict()`, pydantic con `extra="forbid"`, `@JsonIgnoreProperties`), allowlist de tipos en Jackson, cookies firmadas con secreto de servidor, `cosign verify` en el despliegue.
- **Capa de test**: SAST para deserialización; test de integración de mass assignment (`plantillas-de-tests.md`); test negativo de webhook con firma manipulada; verificación de firma o procedencia en el pipeline.
- **ASVS 5.0.0**: v5.0.0-1.5.2, v5.0.0-15.3.3, v5.0.0-3.6.1, v5.0.0-8.2.3 · **CWEs**: CWE-345, CWE-494, CWE-502, CWE-565, CWE-829, CWE-915

## A09:2025 Security Logging & Alerting Failures

**Qué es**: los eventos de seguridad no se registran, se registran mal (con secretos o inyectables) o nadie recibe una alerta que obligue a actuar.
**2021**: A09 Security Logging and Monitoring Failures (renombrada para subrayar la alerta). **Categoría de encuesta**: evalúala con la configuración de logs y alertas, no solo con código.

**Preguntas de diseño**
- ¿Qué eventos se registran: login correcto y fallido, autorización denegada, validación fallida, cambios de permisos?
- ¿Cada evento lleva quién, cuándo, dónde y qué, en formato parseable?
- ¿Los logs salen a un sistema separado y no modificable?
- ¿Hay reglas de alerta y runbooks versionados? Si no están en el repo, márcalo `not_verifiable` y pregunta.

**Señales**
```bash
rg -n -i '(log|logger|console|logging)\.\w+\(.*(password|passwd|token|secret|authorization|cookie|card|ssn)'
rg -n -i '(logger|log)\.(info|warn|error)\(\s*(f["\x27]|["\x27][^"\x27]*["\x27]\s*\+).*(req\.|request\.)'   # log injection
rg -n 'pino|winston|structlog|python-json-logger|logstash-logback|go\.uber\.org/zap|log/slog'
rg -n -i 'login.*(fail|success)|auth(entication)?[._ -]?fail|access[._ -]?denied|forbidden'
rg --files | rg -i '(alert|rules?)[^/]*\.(ya?ml|json)$|runbook|playbook|alertmanager|sentry'
```

- **Compensatorios**: logs de acceso del gateway, audit logs del proveedor de nube, SIEM operado por otro equipo. Cuentan si se documentan; si no, el requisito es `not_verifiable`, no pass.
- **Capa de test**: integración que captura la salida del logger (el login fallido emite un evento con id de usuario e IP y sin la contraseña; plantilla de logging en `plantillas-de-tests.md`); SAST para log injection y secretos en logs. Que alguien responda a la alerta no se puede probar desde el repo: decláralo en "Qué no se revisó".
- **ASVS 5.0.0**: v5.0.0-16.2.1, v5.0.0-16.2.5, v5.0.0-16.3.1, v5.0.0-16.3.2, v5.0.0-16.4.1, v5.0.0-16.4.3 · **CWEs**: CWE-117, CWE-223, CWE-532, CWE-778

## A10:2025 Mishandling of Exceptional Conditions

**Qué es**: la aplicación no previene, no detecta o responde mal a un error: catch que traga, fail-open, transacciones a medias, recursos sin liberar, errores que filtran detalles internos.
**2021**: no existía; recoge CWEs que estaban repartidas.

**Preguntas de diseño**
- En cada punto de decisión de seguridad (authz, validación, pago, verificación de firma): si la dependencia lanza o agota el tiempo, ¿se deniega o se permite?
- ¿Las operaciones de varios pasos se hacen en transacción con rollback completo?
- ¿Hay un handler global que devuelve un mensaje genérico y registra el detalle?
- ¿Se liberan recursos en la ruta de error (`finally`, `with`, `defer`, try-with-resources)?

**Señales**
```bash
rg -n -A3 -t py 'except(\s+Exception)?(\s+as\s+\w+)?\s*:'                       # mira si sigue pass / return True / allow
rg -n -U -t js -t ts 'catch\s*(\(\w*\))?\s*\{\s*\}'                             # catch vacío
rg -n -A2 -t js -t ts 'catch\s*\(\w*\)\s*\{' | rg -n 'next\(\)|return true|allow'
rg -n -U -t java 'catch\s*\(\s*(Exception|Throwable|RuntimeException)\s+\w+\s*\)\s*\{\s*\}'
rg -n -t go '^\s*_\s*=\s*\w+.*\(|,\s*_\s*:?=\s*\w+.*\(|if err != nil \{\s*\}'   # errores ignorados
rg -n 'err\.stack|res\.\w*\(\s*err\s*\)|traceback\.format_exc|printStackTrace|include-stacktrace=always|DEBUG_PROPAGATE_EXCEPTIONS'
rg -n 'unhandledRejection|uncaughtException|@ControllerAdvice|@ExceptionHandler|exception_handler|app\.use\(\s*\(err'
```

- **Compensatorios**: middleware de error global registrado al final, circuit breakers, transacciones gestionadas por el framework (`@Transactional`; comprueba que un catch interno no impide el rollback).
- **Capa de test**: unit e integración de rutas de error, test **fail-closed** (el servicio de políticas lanza o tarda y la petición recibe 403/503, nunca 200), Schemathesis `not_a_server_error` y `negative_data_rejection`, fuzzing (Go native, Atheris, Jazzer). Plantillas fail-closed y A10 en `plantillas-de-tests.md`.
- **ASVS 5.0.0**: v5.0.0-16.5.1, v5.0.0-16.5.2, v5.0.0-16.5.3, v5.0.0-16.5.4, v5.0.0-2.3.3, v5.0.0-16.3.4 · **CWEs**: CWE-209, CWE-248, CWE-252, CWE-390, CWE-396, CWE-460, CWE-636, CWE-703, CWE-755
