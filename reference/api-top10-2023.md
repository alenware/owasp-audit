## Los tres niveles de autorización

Pasa siempre una ruta a `rg` (`.` o la carpeta del componente): sin ruta y sin terminal, `rg` lee stdin y se bloquea.

API1, API3 y API5 son la misma pregunta que A01:2025, hecha **por endpoint** y a tres alturas. Revisa las tres en cada handler; un handler puede aprobar una y fallar otra.

| Nivel | Categoría | Pregunta | Fallo típico en código | Test |
|---|---|---|---|---|
| Objeto | API1 BOLA | ¿Este sujeto puede tocar **este** registro? | Carga por ID sin predicado de propietario o tenant | Dos usuarios: B pide el objeto de A → 403/404 |
| Propiedad | API3 BOPLA | ¿Puede leer o escribir **este campo**? | Serializar la entidad entera; enlazar el body al modelo | Respuesta ⊆ allowlist; PATCH `{role:"admin"}` no cambia nada |
| Función | API5 BFLA | ¿Puede invocar **esta operación**? | Rutas admin protegidas solo por prefijo o por la UI | Matriz rol × endpoint + test de cobertura de rutas |

La matriz de quién debe acceder a qué no sale del código: la redactas como borrador en `docs/security/authz-matrix.yaml` y la confirma una persona (etapa 7).

## Cómo encontrar el ownership check (o su ausencia)

1. **Lista los handlers que reciben un identificador** desde path, query, body, header o argumento GraphQL (sale de `inventory.json`). Incluye exports, descargas, informes, endpoints batch (`ids=[...]`), webhooks que llevan IDs y jobs encolados con un ID del usuario.
2. **Sigue el ID hasta el acceso a datos.** Anota `file:line` en cada salto: handler → servicio → repositorio → consulta.
3. **Busca una de estas formas de control** en ese camino:
   - Consulta con scope: `where: { id, ownerId: user.id }`, `filter(id=pk, org=request.user.org)`, `findByIdAndTenantId`, `WHERE id = $1 AND tenant_id = $2`.
   - Comprobación tras cargar: `if (doc.ownerId !== req.user.id)`, `if obj.owner_id != user.id: raise`.
   - Llamada a política: `authorize(user, "read", doc)`, `can?`, `policy.allows`, `@PreAuthorize("@perm.canRead(#id)")`, `ability.can`, OPA/Cedar/Casbin/Oso.
   - RLS en la base de datos con la identidad propagada en la conexión (`SET app.tenant_id`, `current_setting(...)`).
4. **Comprueba que el control cubre todos los verbos.** Es habitual que GET filtre y PUT/PATCH/DELETE no; que el listado filtre y el detalle no; o que se compruebe el ID del path pero se use el del body.
5. **Recursos anidados**: en `/orgs/:org/projects/:id` no basta con verificar la pertenencia a `org`. Hay que verificar también que `id` pertenece a `org`.
6. **GraphQL**: revisa resolvers de campos anidados y `node(id:)` globales, no solo las queries raíz.
7. Si no encuentras control, registra la búsqueda como evidencia `kind: absence` (`query`, `hits: 0`) y busca compensatorios (gateway, RLS, middleware global) antes de asignar severidad.

```bash
# Accesos por ID (candidatos) y controles de propiedad (deberían aparecer cerca)
rg -n -t js -t ts 'req\.(params|query|body)\.\w*[iI]d\b'
rg -n -t py '(kwargs|path_params|request\.(GET|query_params|data|json))\[?\.?.?\w*_?id'
rg -n -t java '@PathVariable\s*(\(\s*"\w*[iI]d"\s*\))?\s*\w+\s+\w*[iI]d'
rg -n -t go 'chi\.URLParam\(r,\s*"\w*[iI]d"\)|c\.Param\("\w*[iI]d"\)|r\.PathValue\("\w*[iI]d"\)'
rg -n -i '(owner|user|tenant|org|account)_?[iI]d\s*(===?|!==?|:|=)\s*(req\.user|request\.user|currentUser|principal|claims|ctx\.)'
rg -n -i 'authorize\(|can\?|ability\.can|policy\.|@PreAuthorize|enforcer\.Enforce|isAllowed\('
```

**No son controles**: IDs UUID o difíciles de adivinar, ocultar el botón en el frontend, que el token sea válido, que la respuesta cumpla el esquema OpenAPI.

## Aislamiento de tenants

- El tenant sale **del contexto autenticado** (claims del token, sesión), nunca del body, de un query param ni de un header que el cliente controla (`X-Tenant-Id` sin verificar contra el token).
- El aislamiento se impone en la capa de datos: RLS, esquema por tenant, repositorio con scope obligatorio, filtro global del ORM (Hibernate `@Filter`, manager por defecto en Django, extensión de Prisma). Un `WHERE tenant_id` manual en cada consulta es frágil: busca la consulta que lo olvida.
- Revisa también lo que no es la base principal: claves de caché sin tenant, índices de búsqueda, buckets y prefijos de objetos, vector stores (LLM08 en `llm-y-agentes.md`), colas y jobs que pierden el tenant al serializar, exports y backups.
- Las rutas de soporte o superadmin que cruzan tenants deben ser explícitas, auditadas y separadas.

```bash
rg -n -i '(tenant|org|organization|workspace|account)_?[iI]d.*req\.(body|query|headers)|x-tenant'
rg -n -i 'ROW LEVEL SECURITY|CREATE POLICY|current_setting\(|@Filter\(|@TenantId|tenant_scope|set_tenant'
rg -n -i '(cache|redis)\.(get|set)\(\s*[`"\x27][^`"\x27]*\$?\{?(id|key)'      # ¿la clave incluye el tenant?
```

ASVS: v5.0.0-8.4.1. Test: adapta la plantilla BOLA de `plantillas-de-tests.md` con dos usuarios de tenants distintos, y añade el caso en que el cliente envía el `tenant_id` del otro en body o header.

## API1–API10

### API1:2023 Broken Object Level Authorization
Toda función que accede a datos con un ID del usuario necesita control por objeto. Sigue el procedimiento anterior.
**Compensatorios**: RLS con identidad propagada, gateway con política por recurso. **Test**: BOLA con dos usuarios sobre GET, PUT, PATCH y DELETE, más petición sin autenticar → 401. Schemathesis `object_level_authorization`.
**Mapeo**: A01:2025 · CWE-639, CWE-862, CWE-863 · ASVS v5.0.0-8.2.2, v5.0.0-8.3.1, v5.0.0-8.4.1, v5.0.0-8.1.1

### API2:2023 Broken Authentication
Mecanismos de autenticación que permiten robar tokens o suplantar usuarios: JWT mal validados, endpoints de login, OTP o reset sin límites, API keys en URL, tokens que no expiran.
**Busca**: las señales de A07 en `top10-web-2025.md`; además, endpoints que aceptan `?api_key=` o `?token=` (acaban en logs y en `Referer`), y caminos de autenticación alternativos sin la misma fuerza (API key interna que salta el SSO).
**Test**: JWT negativos (sin firma, `alg: none`, `aud` ajeno, expirado), throttling de login y reset, Schemathesis `ignored_auth`.
**Mapeo**: A07:2025 · CWE-287, CWE-307, CWE-798 · ASVS v5.0.0-6.3.1, v5.0.0-9.1.1, v5.0.0-9.2.1, v5.0.0-9.2.3, v5.0.0-7.2.1

### API3:2023 Broken Object Property Level Authorization
Une la excessive data exposure y el mass assignment de 2019: el sujeto puede leer o escribir campos que no debería.
**Busca**: `res.json(user)`, `return model_to_dict(obj)`, entidades JPA devueltas tal cual, `fields = "__all__"`, serializers sin `read_only_fields`; enlace del body al modelo (señales de mass assignment en A08 de `top10-web-2025.md`). Campos sensibles típicos: `password_hash`, `is_admin`, `role`, `tenant_id`, `balance`, `verified`, `internal_notes`.
**Compensatorios**: DTO de salida explícito, esquema estricto de entrada (`additionalProperties: false`, pydantic `extra="forbid"`).
**Test**: mass assignment (PATCH con `role`, `is_verified`, `tenant_id` → sin cambios) y allowlist de claves en la respuesta (`plantillas-de-tests.md`).
**Mapeo**: A01:2025 (exposición, CWE-200, CWE-201) o A08:2025 (mass assignment, CWE-915) · ASVS v5.0.0-8.2.3, v5.0.0-8.1.2, v5.0.0-15.3.1, v5.0.0-15.3.3, v5.0.0-14.2.6

### API4:2023 Unrestricted Resource Consumption
Peticiones que agotan CPU, memoria, almacenamiento, ancho de banda **o dinero**: cada SMS, email, verificación biométrica, llamada a un LLM o a una API de pago es un coste que el atacante puede disparar.
**Busca**: paginación sin máximo (`limit` del usuario sin `min(limit, MAX)`), tamaño de body y de upload sin límite, timeouts ausentes en clientes HTTP y consultas, GraphQL sin límites de profundidad o coste, rate limit ausente por usuario o IP, endpoints que envían SMS/email o llaman a APIs de pago sin cuota ni tope de gasto, operaciones caras (exports, regex, compresión) sin cola.
```bash
rg -n -i '(limit|page_?size|per_?page|take|first)\b.*req\.(query|body)|request\.(GET|args|query_params)\.get\(\s*["\x27](limit|page_size)'
rg -n -i 'bodyParser|express\.json\(|client_max_body_size|MAX_CONTENT_LENGTH|maxFileSize|http\.MaxBytesReader|max-request-size'
rg -n -i 'depthLimit|graphql-depth-limit|costAnalysis|maxDepth|max_depth|query_complexity'
rg -n -i 'twilio|sendgrid|messagebird|vonage|sns\.publish|ses\.send|openai|anthropic|stripe'   # ¿cuota o tope por usuario?
```
**Compensatorios**: límites en gateway o WAF (lee su config), cuotas del proveedor. En CI suelen estar desactivados: confirma la config de producción.
**Test**: N+1 peticiones → 429 con `Retry-After`; `?limit=1000000` se recorta; upload por encima del máximo → 413. La plantilla de rate limit está en `plantillas-de-tests.md`; los demás siguen el mismo patrón. Schemathesis `max_response_time` (desactivado por defecto).
**Mapeo**: A06:2025 (CWE-799, la más cercana; CWE-400 y CWE-770 no están mapeadas en el Top 10:2025, el validador avisará) · ASVS v5.0.0-2.4.1, v5.0.0-15.2.2, v5.0.0-15.1.3, v5.0.0-4.3.1, v5.0.0-5.2.1

### API5:2023 Broken Function Level Authorization
Funciones administrativas o privilegiadas que un usuario normal puede invocar porque la separación de roles es difusa.
**Busca**: rutas `/admin`, `/internal`, `/manage`, `/debug` y verbos destructivos; compara el número de rutas con el de decoradores o middlewares de rol. Desconfía de comprobaciones solo por prefijo (`if path.startsWith("/admin")` en el frontend), de roles leídos del body o de un header, y de endpoints "internos" accesibles desde fuera.
```bash
rg -n -i '["\x27/](admin|internal|manage|ops|debug|superuser)\b' -t js -t ts -t py -t java -t go
rg -n -i '(isAdmin|is_admin|hasRole|has_role|role\s*===?\s*["\x27]admin)'
rg -n -i 'role.*req\.(body|headers)|x-(user-)?role'
```
**Test**: matriz rol × endpoint y test que falla si aparece una ruta no clasificada (`plantillas-de-tests.md`).
**Mapeo**: A01:2025 · CWE-285, CWE-862, CWE-863 · ASVS v5.0.0-8.2.1, v5.0.0-8.1.1, v5.0.0-8.3.1, v5.0.0-8.4.2

### API6:2023 Unrestricted Access to Sensitive Business Flows
Un flujo legítimo (comprar entradas, crear cuentas, canjear cupones, publicar comentarios, referidos) se automatiza a escala y daña el negocio aunque cada petición sea válida.
**Busca**: identifica los flujos valiosos en el threat model (abuse cases); comprueba límites por cuenta y por dispositivo, cuotas por flujo, idempotency keys, CAPTCHA o anti-bot en el servidor (no solo en la UI), tiempos humanos mínimos. Señal en código débil: casi siempre es un hallazgo `DES-`.
**Test**: abuse-case tests concretos (dos canjes del mismo cupón, 100 altas desde el mismo origen). Los escáneres no lo detectan.
**Mapeo**: A06:2025 · CWE-799, CWE-841 · ASVS v5.0.0-2.4.1, v5.0.0-2.4.2, v5.0.0-2.3.2, v5.0.0-2.1.3

### API7:2023 Server Side Request Forgery
El backend pide un recurso remoto a partir de una URI del usuario sin validarla: webhooks configurables, importar desde URL, previsualizar enlaces, avatares remotos, PDF/HTML renderizados en servidor, integraciones OAuth con URL configurable.
**Busca**: las señales SSRF de A01 en `top10-web-2025.md`; luego comprueba allowlist de esquema, host y puerto, resolución DNS y validación de la IP final (DNS rebinding), redirecciones desactivadas (`redirect: "manual"`, `allow_redirects=False`, `CheckRedirect`), y bloqueo de rangos privados y de metadata (169.254.169.254, `fd00:ec2::254`).
**Compensatorios**: proxy de egress con allowlist, NetworkPolicy, IMDSv2 con hop limit 1 (rebaja impacto, no refuta).
**Test**: integración con `http://127.0.0.1`, `http://169.254.169.254/`, IP en decimal u octal, redirección 302 hacia localhost → rechazado. SSRF ciego necesita infraestructura OAST (fuera de CI).
**Mapeo**: A01:2025 · CWE-918 · ASVS v5.0.0-1.3.6, v5.0.0-13.2.4, v5.0.0-13.2.5, v5.0.0-15.3.2, v5.0.0-13.1.1

### API8:2023 Security Misconfiguration
Igual que A02 aplicada a la API: CORS permisivo con credenciales, errores verbosos, métodos innecesarios (TRACE), falta de TLS, headers ausentes, parsers con funciones peligrosas.
**Busca**: señales de A02 y de A10 (stack traces) en `top10-web-2025.md`; `Access-Control-Allow-Origin` que refleja el `Origin` con `Allow-Credentials: true`.
**Test**: ZAP API scan, test de CORS con origen no permitido, test de error genérico.
**Mapeo**: A02:2025 · CWE-16, CWE-489, CWE-942 · ASVS v5.0.0-3.4.2, v5.0.0-13.4.2, v5.0.0-13.4.4, v5.0.0-16.5.1, v5.0.0-3.4.1

### API9:2023 Improper Inventory Management
Hosts, versiones o endpoints que nadie documenta o vigila: `/v1` antiguo todavía desplegado, rutas de debug, entornos de staging públicos, documentación interna expuesta.
**Busca**: compara las rutas del router con el OpenAPI (shadow endpoints sin documentar, zombie endpoints de versiones viejas); rutas de debug, health y métricas; introspección GraphQL en producción; Swagger UI expuesto; flags que montan rutas solo en ciertos entornos.
```bash
rg --files | rg -i '(openapi|swagger)\.(ya?ml|json)$'
rg -n -i '["\x27]/(v0|v1|beta|old|legacy|test|debug|_debug|internal|actuator|metrics|pprof|graphiql|playground)\b'
rg -n -i 'swagger-ui|SwaggerModule\.setup|springdoc|drf_spectacular|introspection\s*[:=]\s*true|playground\s*[:=]\s*true'
```
**Compensatorios**: rutas montadas solo en desarrollo (verifica la condición y qué valor tiene en producción), gateway que publica solo las rutas del spec.
**Test**: test que falla si el router expone rutas que no están en el OpenAPI; Schemathesis `unsupported_method`. El inventario entre entornos y gateways es operativo: lo que no se vea en el repo va a "Qué no se revisó".
**Mapeo**: A02:2025 (CWE-489; mapeo por inferencia, no oficial) · ASVS v5.0.0-13.4.5, v5.0.0-15.2.3, v5.0.0-4.3.2, v5.0.0-13.1.1

### API10:2023 Unsafe Consumption of APIs
Se confía más en las respuestas de APIs de terceros que en la entrada del usuario: se usan sin validar, se siguen redirecciones a ciegas, no hay TLS validado ni timeouts.
**Busca**: respuestas externas que llegan a sinks (SQL, HTML, shell, rutas de archivo, URLs que se vuelven a pedir) sin validación de esquema; clientes HTTP sin timeout; `verify=False` hacia terceros; reintentos sin límite; datos del tercero guardados como confiables.
**Test**: contract test con el tercero simulado devolviendo payload enorme, malformado, con inyección o con redirección a 127.0.0.1 → la app valida, corta por tiempo y no sigue la redirección.
**Mapeo**: A08:2025 (CWE-345) o A05:2025 si acaba en un sink de injection · ASVS v5.0.0-15.3.2, v5.0.0-12.3.2, v5.0.0-13.2.4, v5.0.0-16.5.2, v5.0.0-2.2.1

## Schemathesis y fuzzing con dos identidades

- Schemathesis (v4) trae `object_level_authorization`: comprueba que un usuario no lee el objeto de otro. **Exige al menos dos `peers` configurados en `[auth.wfc]`**, es decir, dos identidades reales con datos propios. Sin ellos el check no prueba nada.
- `ignored_auth` comprueba que el endpoint rechaza credenciales ausentes o inválidas; `use_after_free` que un recurso borrado ya no es accesible; `unsupported_method` sirve para API9; `max_response_time` para API4.
- Ejecuta solo contra localhost o contra un staging cuyo host haya dado el usuario en el chat. Nunca contra producción.

```bash
st run http://localhost:8000/openapi.json --checks object_level_authorization,ignored_auth,use_after_free   # (verificar flags)
# Los peers van en el archivo de configuración de Schemathesis, sección [auth.wfc]   (verificar flags)
```

- RESTler tiene un checker de namespace con dos usuarios parecido (verificar flags). Burp con Autorize o AuthMatrix sirve para revisión manual, no como puerta de CI.
- Un escaneo DAST sin autenticar no evalúa API1, API3 ni API5. Si solo se ejecutó eso, dilo en el informe.
